# Data Identity (`dataID`) in the Generated React App

This document describes the **data identity structure** used throughout the
React/TypeScript applications generated by `judo-ui-react`. It explains the
identity-bearing fields that every stored entity carries, their format, where
they originate, and how the generated templates use them for routing, tables,
selection, CRUD, and backend calls.

> **Terminology note.** There is no field literally named `dataID` in the
> templates. In this codebase the "data id" concept is split into two distinct
> fields — `__identifier` (a client-side row identity) and `__signedIdentifier`
> (a backend-issued, signed handle) — plus a small set of capability/state
> metadata fields. MUI's DataGrid also exposes the row identity through its own
> `data-id` DOM attribute, which is wired to `__identifier`. All of these are
> documented below.

---

## 1. Where data identity comes from

The generated app is produced in **two phases**:

1. **Phase 1 — TypeScript REST layer** (`judo-ui-typescript-rest-template`):
   generates the data-api types, including the base identity interfaces
   `JudoIdentifiable<T>` / `JudoStored<T>` and the per-class `XxxStored` types.
   These types declare the `__`-prefixed metadata fields.
2. **Phase 2 — React UI** (this repo, `judo-ui-react`): consumes those types and
   uses the identity fields in routing, tables, cards, dialogs, and actions.

Because the interfaces themselves are emitted by Phase 1, you will **not** find a
`JudoStored.ts` definition inside this repository. You will find their *usage*
throughout `judo-ui-react/src/main/resources/actor/...`, and the import path the
templates rely on:

```ts
import type { JudoStored } from '~/services/data-api/common/JudoStored';
```

Every stored entity in the generated app is typed as `XxxStored extends
JudoStored<Xxx>`, so it always carries the identity metadata fields.

## 2. The identity / metadata fields

Every stored object the backend returns carries a set of double-underscore
(`__`) prefixed metadata fields. These are *not* business attributes — they are
framework-managed identity and capability markers.

| Field | Type | Purpose | Origin |
|-------|------|---------|--------|
| `__identifier` | `string` | **Client-side row identity.** Stable key used by React/MUI for row keys, selection, lookups, and edit-state mapping. | Backend response |
| `__signedIdentifier` | `string` | **Backend handle.** A cryptographically signed reference to the persisted instance. Used in URLs and as the parameter that identifies an instance when calling backend services. | Backend response (signed) |
| `__updateable` | `boolean` | Capability flag: whether the current principal may update this instance. | Backend response |
| `__deleteable` | `boolean` | Capability flag: whether the current principal may delete this instance. | Backend response |
| `__selected` | `boolean` | Association/selection state: whether this row is already linked/selected on the backend (used by association tables). | Backend response |

### 2.1 `__identifier` vs `__signedIdentifier`

These two fields look similar but serve different roles, and confusing them is
the most common source of bugs:

```
   __identifier                         __signedIdentifier
   ────────────                         ──────────────────
   • client-facing row id               • backend-facing instance handle
   • used as React key / MUI getRowId   • used in route URLs ( /:signedIdentifier )
   • used for in-memory lookups,        • passed to service calls to identify
     selection diffing, edit modes        the target instance
   • appears in the DOM as data-id      • signed -> safe to expose in URLs
```

- Use **`__identifier`** whenever you are working *inside the browser*: keying
  list/grid rows, finding a row from a DOM event, tracking which rows are in
  edit mode, computing selection diffs.
- Use **`__signedIdentifier`** whenever you are *crossing the boundary to the
  backend or the router*: building a deep-link URL, navigating to a view page,
  or telling a service which instance to read/update/remove/export.

## 3. `__identifier` — client-side row identity

### 3.1 As the MUI DataGrid row id

The generated tables tell MUI DataGrid to use `__identifier` as the row id:

`judo-ui-react/.../components/table/LazyTable.tsx.hbs` and `EagerTable.tsx.hbs`:

```ts
const getRowIdentifier: (row: T) => string = (row) => row.__identifier!;
// ...
<DataGrid
  getRowId={getRowIdentifier}
  ...
/>
```

Because `getRowId` returns `__identifier`, MUI renders each row's DOM element
with a matching `data-id` attribute. That is how `data-id` and `__identifier`
become two views of the same value.

### 3.2 The `data-id` DOM attribute → row lookup

When the table's context menu handles a right-click, it reads MUI's `data-id`
attribute back off the DOM and resolves it to the underlying row object via
`__identifier`:

`judo-ui-react/.../components/table/ContextMenu.tsx.hbs`:

```ts
const row = event.currentTarget.parentElement!.getAttribute('data-id')!;
const rowData = data.find((d) => d.__identifier === row);
```

So the round-trip is:

```
   row object .__identifier
        │  (MUI getRowId)
        ▼
   <div data-id="...">          DOM
        │  (getAttribute('data-id'))
        ▼
   data.find(d => d.__identifier === row)   →  back to the row object
```

### 3.3 Keys, edit state, and selection

`__identifier` is the stable key used in several places:

- **React list keys** for cards: `key={d.__identifier}`
  (`components/widgets/CardsContainer.tsx.hbs`, `DefaultCard.tsx.hbs`).
- **Row edit-mode mapping** in tables:
  `rowModesModel[row.__identifier]?.mode === GridRowModes.Edit`
  (`LazyTable.tsx.hbs`, `EagerTable.tsx.hbs`, `table-row-actions.tsx.hbs`).
- **Row-level validation** mapping in relation columns:
  `rowValidation.current.has(props.row.__identifier)`
  (`fragments/relation/column.fragment.hbs`, where the column is also told
  `identifierAttribute={'__identifier'}`).
- **Selection diffing** in `utilities/table.ts.hbs`
  (`getUpdatedRowsSelected`, `isRowSelectable`): selected rows are matched by
  `r.__identifier === selection`.

## 4. `__signedIdentifier` — backend handle & routing

### 4.1 In route definitions

Pages that operate on a specific instance get a `:signedIdentifier` URL segment.
Whether a page needs one is decided by `UiPageHelper.pageHasSignedId(page)`
(`judo-ui-react/src/main/java/.../UiPageHelper.java`):

```java
public static boolean pageHasSignedId(PageDefinition page) {
    if (isSingleAccessPage(page) || page.isOpenInDialog()) {
        return false;
    }
    // ... member-type access / refreshable output pages ...
    return true;
}

public static String getPageRoute(PageDefinition page) {
    if (page.isDashboard()) return "";
    String suffix = pageHasSignedId(page) ? "/:signedIdentifier" : "";
    return pagePath(page) + suffix;
}
```

The route helper functions in `routes.tsx.hbs` therefore take the signed id as
an argument and substitute it into the path:

```ts
export const routeToSomePage = (signedIdentifier: string): string =>
  'Some/Path/:signedIdentifier'.replace(/:signedIdentifier/, signedIdentifier);
```

Pages that do not need an instance handle generate a no-argument variant:

```ts
export const routeToSomePage = (): string => 'Some/Path';
```

### 4.2 Reading it back in the page

The page component reads the segment with React Router's `useParams` and seeds
its owner/data state from it (`pages/index.tsx.hbs`):

```ts
const { signedIdentifier } = useParams();
owner.current = { __signedIdentifier: signedIdentifier };
// ...
const [data, setData] = useState<XxxStored>(
  { __signedIdentifier: signedIdentifier } as XxxStored
);
```

### 4.3 Passing it to services

When a page calls a backend service it identifies the target instance with a
synthetic object carrying only `__signedIdentifier`. The Java helper
`UiActionsHelper.refreshActionDataParameter(...)` emits this literal:

```java
if (pageHasSignedId(pageDefinition)) {
    return "{ __signedIdentifier: signedIdentifier } as any";
}
```

This pattern appears across action fragments
(`pages/actions/*.fragment.hbs`), for example:

```ts
// RefreshAction
return serviceImpl.list({ __signedIdentifier: signedIdentifier } as any, queryCustomizer);

// RemoveAction
await serviceImpl.remove({ __signedIdentifier: signedIdentifier } as any, [target]);

// ExportAction
await serviceImpl.export({ __signedIdentifier: signedIdentifier } as any, queryCustomizer);

// create/update within a table page (pages/index.tsx.hbs)
await serviceImpl.createRelation({ __signedIdentifier: signedIdentifier } as any, rowData, queryCustomizer);
await serviceImpl.updateRelation({ __signedIdentifier: signedIdentifier } as any, rowData);
```

### 4.4 Navigating after an operation

After creating an instance or calling an operation, the result's
`__signedIdentifier` is used to navigate to the target view page
(`OpenPageAction`, `OpenCreateFormAction`, `*CallOperationAction` fragments):

```ts
navigate(routeToSomeViewPage(result.__signedIdentifier));
```

### 4.5 Single-access pages

For single-access (singleton) pages there is no URL segment; instead the host
handle is held in a ref:

```ts
const singletonHost = useRef<{ __signedIdentifier: string }>(
  {} as unknown as { __signedIdentifier: string }
);
```

## 5. Capability flags — `__updateable`, `__deleteable`, `__selected`

These backend-supplied booleans gate UI behavior. The generated code always
checks both the model-level capability **and** the per-instance flag, so the UI
reflects row-level authorization.

### 5.1 `__updateable` / `__deleteable`

`pages/index.tsx.hbs` and `dialogs/index.tsx.hbs`:

```ts
// can the form be saved?
return <isPageUpdateable> && typeof data?.__updateable === 'boolean' && data?.__updateable;

// can the instance be deleted?
return <isPageDeleteable> && typeof data?.__deleteable === 'boolean' && data?.__deleteable;
```

Tables hide the inline-edit action when a row is not updateable
(`LazyTable.tsx.hbs`, `EagerTable.tsx.hbs`):

```ts
hidden: (row: any) =>
  rowModesModel[row.__identifier]?.mode === GridRowModes.Edit
  || !editable
  || row.__updateable === false,
```

Relation link widgets use `__deleteable` to decide whether the unset/remove
control is shown (`containers/components/link/index.tsx.hbs`):

```ts
dropDownButtonIsVisible: (value: any) =>
  exists(value) && !readOnly && !isRequired && value.__deleteable && !!actions.someAction,
```

### 5.2 `__selected` — association tables

`__selected` indicates whether a candidate row is already linked on the backend.
The `isRowSelectable` helper (`utilities/table.ts.hbs`) uses it to decide whether
a row can be (re)selected in association/aggregation selector tables:

```ts
export const isRowSelectable = <T extends JudoStored<T>>(
  row: T & { __selected?: boolean },
  single?: boolean,
  alreadySelectedItems?: T[],
) => {
  if (Array.isArray(alreadySelectedItems) && alreadySelectedItems.length) {
    // aggregation tables: compare against the caller's in-memory list by __identifier
    return !alreadySelectedItems.find(i => i.__identifier === row.__identifier);
  } else if (!single || typeof row?.__selected === 'boolean') {
    // association relations: trust the backend's __selected flag
    return !row.__selected;
  }
  // single aggregations: allow, so users can re-set a just-unset value
  return true;
};
```

This logic is unit-tested in `utilities/table.test.ts`, where the mock stored
type illustrates the minimal identity shape:

```ts
interface TestType extends JudoStored<TestType> { name: string }
interface ResponseTestType extends TestType { __selected?: boolean }

const baseType = { __signedIdentifier: 'test-sid' };
```

## 6. Format / value semantics

- **`__identifier`** — an opaque string. Treat it as a black-box key; do not
  parse it. It is unique within a result set and stable enough to use as a React
  key and grid row id. It is safe to expose in the DOM (`data-id`) but is **not**
  the value you send to the backend to address an instance.
- **`__signedIdentifier`** — an opaque, signed string. Because it is signed it is
  safe to place in URLs and to pass to services. Do not synthesize or mutate it
  on the client; only ever forward a value originally issued by the backend
  (the one exception being the placeholder objects like
  `{ __signedIdentifier: signedIdentifier }` whose value still came from the
  route param, which itself came from a backend-issued link).
- **`__updateable` / `__deleteable` / `__selected`** — booleans. Code defensively
  checks `typeof x === 'boolean'` before trusting them, because a transient
  (not-yet-persisted) object may not carry them.

## 7. End-to-end flow summary

```
   ┌──────────────────────────────────────────────────────────────────┐
   │  Backend returns XxxStored with:                                  │
   │    __identifier, __signedIdentifier, __updateable,                │
   │    __deleteable, __selected                                       │
   └───────────────┬───────────────────────────────┬──────────────────┘
                   │                                │
         client-side identity                backend handle
                   │                                │
                   ▼                                ▼
   ┌───────────────────────────┐    ┌──────────────────────────────────┐
   │ __identifier              │    │ __signedIdentifier               │
   │  • getRowId (MUI)         │    │  • route param /:signedIdentifier │
   │  • data-id DOM attr       │    │  • routeToXxx(signedIdentifier)   │
   │  • React keys             │    │  • service calls                 │
   │  • selection / edit state │    │    { __signedIdentifier } as any  │
   │  • row-level validation   │    │  • post-action navigation        │
   └───────────────────────────┘    └──────────────────────────────────┘
                   │                                │
                   ▼                                ▼
         __updateable / __deleteable / __selected gate UI capabilities
```

## 9. Canonical test IDs and browser-state isolation

Generated tables expose stable `data-testid` values through
`utilities/transfer-id.ts`. The table identifier is the element identity
(`sourceId` when present, otherwise the sanitized `xmi:id`), and the row
identifier resolves in this order: `__signedIdentifier`, `__identifier`,
`__tempId`, `id`, then `idx-<index>`.

| Target | Test-ID grammar |
| --- | --- |
| table | `table::<table-id>` |
| row | `table::<table-id>::row::<transfer-id>` |
| cell | `table::<table-id>::row::<transfer-id>::cell::<field>` |
| selection cell | `table::<table-id>::row::<transfer-id>::cell::__check__` |
| filter panel | `table::<table-id>::filter-panel` |
| filter inputs | `...::column`, `...::operator`, `...::value` |
| row action | `table::<table-id>::row::<transfer-id>::action::<role>` |
| role-less action | `button::<button-id>::<action-type>` |

The normalized row-action roles are `set`, `create`, `view`, and `delete`;
other model action types remain their raw normalized action type. `overflow`
is reserved for the dropdown trigger. `edit`, `save`, and `cancel` are reserved
template-only inline-edit roles until the runtime exposes matching controls.

Browser storage is scoped to the application's base path. Every persisted key
uses `judo:<namespace>:<key>`, where `/RelationTest/Actor/` becomes
`RelationTest.Actor` and the root path becomes `root`. This prevents React and
runtime actors served from one origin from overwriting each other's OIDC,
layout, and local state.

Two cross-engine limits remain:

- The runtime has no inline-edit `edit`, `save`, or `cancel` control test IDs.
  Those selectors are template-only until runtime support is added.
- Unsaved rows are not selector-identical across engines. This template uses
  `temp::<ms>::<7-hex>`; the runtime uses `temp::<ms>::<base36>` for CRUD and
  `inline-<n>` for inline creation. Tests must discover unsaved row IDs from
  the DOM rather than construct a cross-engine selector.
