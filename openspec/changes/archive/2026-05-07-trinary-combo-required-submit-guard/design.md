## Context

Two prior facts shape this design:

1. The previous fix `JNG-6398` (archive `2026-05-04-trinary-combo-required`) intentionally scoped itself to the visual layer of `TrinaryLogicCombobox.tsx.hbs`. Its design.md explicitly noted that "submitting a value the user did not consciously pick is worse than letting required-field validation surface the missing pick" — but it never actually wired up the missing-pick surfacing on the client side. The form action still submits an `undefined` payload to the backend. The user's complaint is that this contradicts the project's own client-side guard pattern.

2. The project already has a working client-side guard:

   ```
   ┌─────────────────────────────────────────────────────────┐
   │  Generated form action (CreateAction / UpdateAction)    │
   ├─────────────────────────────────────────────────────────┤
   │  if (hasPageRequiredBy(page)) {                         │
   │    {{> local-validate.fragment.hbs }}                   │
   │       └─▶ requiredByRecord = { attr: !!data.<flag>, …}  │
   │       └─▶ passesLocalValidation(...) → if false: return │
   │  }                                                      │
   │  // … then call backend                                 │
   └─────────────────────────────────────────────────────────┘
   ```

   `requiredByRecord` is generated by walking the page's visual tree and picking widgets whose `requiredBy` reference is non-null. Statically-required attributes (`isRequired = true` on the metamodel) are not collected, so `passesLocalValidation` never sees them.

3. The existing `TRINARY_LOGIC` map maps `null`/`undefined` → `'Unknown'`. The previous fix forced the visual `<Select>` `value` to `''` when `required && value == null`, but `data[attr]` in form state is still `undefined`. So `failsRequired(input)` in `passesLocalValidation` will correctly classify it as missing — once we get the entry into `requiredByRecord`.

This is a thin extension of the existing pattern, not a new mechanism.

## Goals / Non-Goals

**Goals:**
- Block form submission when a required `TrinaryLogicCombo` value is `null`/`undefined`/`''`, using the existing `passesLocalValidation` flow.
- Reuse `requiredByRecord` and the `local-validate.fragment.hbs` machinery — no new utility, no parallel code path.
- Keep the standardized `${id}-undefined` testid surface that JNG-6381 just hardened.
- Keep filter contexts unaffected (no `required` passed → no submit-guard entries → 3-option behavior unchanged).
- Lock the new behavior into snapshots so a future regression in the helper or fragment is caught by `judo-diff-checker-maven-plugin`.

**Non-Goals:**
- Generalize the submit guard to all statically-required scalar inputs (text, numeric, date, enum, …). That's a worthwhile cleanup but a much larger blast radius across snapshots; explicitly deferred to a separate proposal.
- Validate the action-driven dynamic case (`actions.isXxxRequired(...)`) on the client side. The Java helper cannot see runtime action results; this stays a backend-rejection case for now (documented as Open Question in this design).
- Default-select `false` on required booleans. Same rationale as the previous design: silent submission of an unchosen value is worse than blocking submit with the existing `MISSING_REQUIRED_ATTRIBUTE` message.
- Touch the Pro itest. Mirror demo for `ActionGroupTestPro` is a follow-up.
- Touch metamodel, helpers other than `UiPageHelper`, template parameters, or i18n.

## Decisions

### Decision 1: Extend `getRequiredByWidgetsForPage()` rather than introduce a sibling `getStaticallyRequiredTrinaryWidgets()`

```java
// UiPageHelper.java
public static List<VisualElement> getRequiredByWidgetsForPage(PageDefinition pageDefinition) {
    Set<VisualElement> elements = new LinkedHashSet<>();
    collectVisualElementsMatchingCondition(
        pageDefinition.getContainer(),
        (element) -> element.getRequiredBy() != null
            || isStaticallyRequiredTrinaryCombo(element),  // new clause
        elements);
    return elements.stream().sorted(Comparator.comparing(NamedElement::getFQName)).collect(Collectors.toList());
}

private static boolean isStaticallyRequiredTrinaryCombo(VisualElement element) {
    return element instanceof TrinaryLogicCombo combo
        && combo.getAttributeType() != null
        && combo.getAttributeType().isIsRequired();
}
```

**Rationale.** A single collection feeds a single `requiredByRecord`. Splitting into two helpers would force the fragment to merge two lists, deduplicate, and re-sort — all for the same downstream effect. `hasPageRequiredBy` then automatically returns true whenever either source is present, so `passesLocalValidation` is imported and called without further wiring.

**Alternative rejected.** A new helper `getStaticallyRequiredTrinaryWidgetsForPage()` plus a new `hasStaticallyRequiredTrinary` Handlebars guard. Doubles the Handlebars surface and the test surface for no benefit.

### Decision 2: Emit `true` literal in `requiredByRecord` for static-required entries

```handlebars
{{# each (getRequiredByWidgetsForPage page) as |child| }}
  {{# if child.attributeType }}
    {{# if child.requiredBy }}
      {{ child.attributeType.name }}: !!data.{{ child.requiredBy.name }},
    {{ else }}
      {{ child.attributeType.name }}: true,
    {{/ if }}
  {{ else }}
    …  (relation case, unchanged)
  {{/ if }}
{{/ each }}
```

**Rationale.** `passesLocalValidation` already does `failsRequired(data[attr]) && requiredByRecord[attr]`. A literal `true` makes the static-required intent explicit in the generated TypeScript, doesn't require a helper change, and preserves a trivial code-path for tooling/linters reading the snapshot.

**Alternative rejected.** Always emit `!!data.<requiredBy>` and rely on a sentinel attribute name when there is no `requiredBy`. Brittle and harder to read.

### Decision 3: Preserve `${id}-undefined` testid via a hidden anchor MenuItem

```tsx
<MenuItem className="trinary-logic-combobox-item" data-testid={`${id}-true`} value={'Yes'}>{ … }</MenuItem>
<MenuItem className="trinary-logic-combobox-item" data-testid={`${id}-false`} value={'No'}>{ … }</MenuItem>
{required ? (
  <MenuItem
    sx={ { display: 'none' } }
    aria-hidden="true"
    disabled
    data-testid={`${id}-undefined`}
    value={'__hidden__'}
  />
) : (
  <MenuItem className="trinary-logic-combobox-item" data-testid={`${id}-undefined`} value={'Unknown'}>
    { t('judo.component.TrinaryLogic.unknown', { defaultValue: 'Unknown' }) as string }
  </MenuItem>
)}
```

**Rationale.** JNG-6381 standardized testid surfaces. Dropping `${id}-undefined` in the required case silently shrinks that surface and risks downstream test breakage. A `display: none`, `disabled`, `aria-hidden` MenuItem keeps the testid queryable for "is the unknown option absent / non-actionable?" assertions, while remaining unselectable and invisible to end users. MUI accepts unrendered MenuItems as Select children.

**Alternative rejected.** Drop the testid entirely (status quo of the previous fix). Saves one DOM node but breaks the JNG-6381 contract.

**Alternative rejected.** Render the testid on a non-MenuItem (`<span hidden data-testid=… />`). MUI `<Select>` complains about non-MenuItem children, and the placement looks accidental in the snapshot.

### Decision 4: `ActionGroupTest` snapshot is the regression contract; no new module

Verification surface (matches the previous archive's "verification triangle"):

```
┌─────────────────────────────────────────────────────────┐
│  1. Java unit / integration build                       │
│     UiPageHelper change is exercised by every itest.    │
├─────────────────────────────────────────────────────────┤
│  2. Snapshot diff in ViewGalaxyForm + Galaxy page action│
│     locks in:                                           │
│       • passesLocalValidation import + call             │
│       • requiredByRecord = { discoveryConfirmed: true } │
│       • TrinaryLogicCombobox testid preservation        │
├─────────────────────────────────────────────────────────┤
│  3. Manual `pnpm dev`: required combo blocks submit     │
│     when left empty; optional combo still submits null. │
└─────────────────────────────────────────────────────────┘
```

The previous archive already added `discoveryConfirmed` (required) and `archived` (optional) to `Galaxy`. We reuse the same model — no new attributes. Only the snapshots that capture the page action change need refreshing.

### Decision 5: Filter contexts stay opt-out by omission

`FilterDialog.tsx.hbs` and `SingleValueFilterComponent.tsx.hbs` do not pass `required`. They also do not call `passesLocalValidation`. Since `getRequiredByWidgetsForPage` only walks `pageDefinition.getContainer()` for forms/dialogs, filter widgets are not visited and cannot pollute `requiredByRecord`. No change needed; this design simply preserves that property by construction.

## Risks / Trade-offs

- **Snapshot churn beyond `ViewGalaxyForm.tsx`.** Any itest page that already contains a `requiredBy` widget now generates an identical record (fine), but pages with statically-required trinary combos newly import `passesLocalValidation` and gain a `requiredByRecord`. Today only `ActionGroupTest`'s `Galaxy` form has such a widget (introduced by the previous archive), so blast radius is one form-action snapshot file. Mitigation: scope task list to that single snapshot; full root build (CI) confirms no other itest is affected.
- **Hidden testid anchor breaks an unknown downstream consumer.** The hidden MenuItem is a new DOM node. Mitigation: explicit `aria-hidden="true"` and `display: none`; consumers that previously asserted "the `${id}-undefined` element is absent for required fields" will need to switch to "the `${id}-undefined` element exists but is `display: none`" — documented in the migration note in the proposal.
- **Action-driven required is still backend-only.** Documented as a known gap (see Open Questions).
- **Reactive flip semantics.** When `actions.isXxxRequired` flips a field from optional to required at runtime, the option list updates (existing behavior), but the submit guard does not — it is built at code-gen time from the static `isRequired` flag. This is consistent with how `requiredBy`-driven dynamic required already works (the runtime `data.<flag>` decides at submit), so the divergence is between metamodel-static and action-dynamic, not introduced by this change.

## Open Questions

1. **Should a future change broaden the submit guard to all statically-required scalar inputs (text/numeric/date/enum/…)?** Out of scope here. Track as follow-up; the fragment shape introduced here generalizes without rewrite.
2. **Should `actions.isXxxRequired(...)` participate in submit-guard?** Would require building `requiredByRecord` partly at runtime. Out of scope; currently no project pattern for it.
3. **Pro itest mirror.** Carry the demo into `ActionGroupTestPro` for parity? The previous archive deferred this; we keep that posture.
